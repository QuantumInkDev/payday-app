Design · Approved 2026-11-14

PayDay Multi-Platform

One set of bills and pay periods that follows a person across Windows, macOS, iOS, Android and the web. It is synced through their own cloud drive, encrypted so only their devices can read it, and has a three-click Notion connection for anyone who wants their bills there.

1Intent

PayDay works well as a Windows app. The goal is to make it a product that follows a person across every device: Windows (done), macOS, iOS and Android, all showing the same data, with no visible sync step. The end game is the public app stores Decided. Setup has to be short enough that a stranger gets through it, and security has to be good enough to hold their financial data.

Notion sync works but takes about ten manual steps: create an integration, copy a token, build three databases, share each one. That is acceptable for the developer and a dealbreaker for everyone else.

2Goals and limits

Goals

  • Data entered on any device shows up on the others without the user doing anything.
  • Works fully offline and syncs when the network returns.
  • Costs nothing to run at any number of users, for the user and the developer.
  • The cloud provider never sees readable financial data (end-to-end encryption).
  • A new user is set up in a few taps. Adding a second device takes about a minute.
  • Data stays portable: JSON export and import keep working on every platform.
  • Notion stays available as an optional add-on, with a much simpler connection.

Non-goals for this design

  • Bank linking or transaction import.
  • A web app that keeps data on a server. The web app in §6.7 keeps data in the browser and the user's drive, like every other device.
  • Accounts, sign-up, or a server holding user data.
  • Sharing a plan with a partner. It's a feature candidate (§9) and isn't built here. The sync format doesn't depend on where the vault is stored, so a later shared vault can live in an ordinary shared folder. That keeps partners on different cloud accounts possible.

Anti-goals

Works technically, still fails

  • Any path where the developer or the cloud provider can read a user's data.
  • A sync that silently drops or reverts an edit.
  • Setup longer than the current Notion flow.
  • The four apps disagreeing about the numbers: which bills fall in which pay period, totals, payoff dates.

3Constraints

  • The Windows app is WinUI 3 on .NET 9 (net9.0-windows10.0.26100.0), used daily on an arm64 VM. It can only be built on Windows. This Mac has Xcode and Swift but no dotnet.
  • Windows builds run on the VM from the Mac. The arm64 VM is the Parallels guest "Win 11 Arm Dev" on this Mac, and prlctl exec "Win 11 Arm Dev" … runs commands in it without SSH. That was verified on 2026-11-14 (.NET SDK 9.0.318, clone at C:\Projects\PayDayApp). Those commands run as NT AUTHORITY\SYSTEM, so building and testing work but launching the packaged app doesn't. Launching still needs the interactive session; Parallels' --current-user option is worth trying. Remote builds use tools/vm-build.sh, which keeps its own checkout at C:\Builds\payday-app and never touches the daily clone C:\Projects\PayDayApp; push before running it.
  • Hosting is on the Quantum Ink team's paid Vercel plan, so commercial use is covered.
  • Browsers can erase a site's stored data. Safari does it after 7 days without a visit unless the site is installed. That's how the original payday.html lost its data, and it shapes the web app (§6.7).
  • PayDay.Core and PayDay.Tests are plain net9.0. Their 194 passing tests encode current behaviour: pay periods including the 3 PM early start, payoff math, the backup format and the Notion mapping.
  • Free hosted databases and sync services all pause or delete idle free projects (Supabase, PowerSync, Appwrite, Couchbase). ElectricSQL is winding down and Realm sync is shut down (research, 2026-11-14). That is why this design uses the user's own cloud storage.
  • iCloud Drive has no supported API on Windows or Android.
  • The Notion OAuth token exchange needs a client secret that can't ship inside an app.
  • App-store distribution needs a privacy policy URL, and Notion's public-integration form needs a privacy policy and a terms URL.
  • Existing data must survive. The developer's live Windows database and Notion workspace are the starting point.

4Approaches

Where synced data lives

ApproachTrade-off
User's own cloud drive, encrypted change files Decided$0 at any scale, the provider sees only ciphertext, no accounts. We write and test the merge logic ourselves and maintain two or three drive integrations.
Small relay service we run, storing only ciphertextSimplest onboarding with no drive sign-in, but it's a service to run and pay for, and it needs the same merge logic.
PowerSync + SupabaseThe most finished engine, but about $75 a month or self-hosting. Accounts are required, and end-to-end encryption defeats most of what it offers.

Picked because the user is fine with personal cloud sync, it keeps the promise that it's free and nobody can read your data, and the data is small: tens of bills and hundreds of payments a year.

Sharing the core logic across four apps

ApproachTrade-off
Native code per platform plus a shared conformance suite DecidedEach app is idiomatic in its own language, and the existing C# core and tests carry over. The logic is written three times (C#, Swift, Kotlin), so the versions can drift. Shared test fixtures that every app must pass catch that.
One Rust core with bindings to all four appsLogic is written once and can't drift. It costs a new language and harder cross-platform builds and debugging, and the C# core gets rewritten.
Kotlin Multiplatform coreCovers Android, iOS and macOS but not Windows on arm64. Rejected.

Simplifying Notion

ApproachTrade-off
Notion public integration with OAuth, where the app creates its own databases Claude's callThree clicks for the user. Needs a tiny stateless function to hold the client secret.
Keep the token-paste flow and add a guided wizardNo function to host, but still about six steps.
OAuth with template duplicationWorks, but Notion now recommends creating content through the API, and a template drifts from the code.

The web app

ApproachTrade-off
Local-first TypeScript web app, served as static files from Vercel Web app decided TypeScript is Claude's callMatches the Next.js-on-Vercel stack SpellThat already uses, and has the most mature browser tooling: SQLite in WebAssembly, WebCrypto, and drive sign-in without a secret. The cost is a fourth language that has to pass the conformance suite.
Blazor WebAssembly reusing PayDay.CoreThe C# rules aren't rewritten, but the screens get rebuilt anyway, the first download is several MB, and keeping SQLite in the browser is fiddlier.

6Sync design

Each device writes only its own folder and reads everyone else's. The vault key never leaves the devices.

6.1 Data model changes on all platforms

  • Every synced row gets a globally unique ID. Bills added in the app use GUID strings, but the seeded bills use "1"–"27" (apps/windows/PayDay/Services/SeedData.cs). Seed IDs get rewritten to GUIDs, and Payments and Snapshots move from INTEGER AUTOINCREMENT to string IDs (UUIDv7) Claude's call. That way rows created on two devices never collide. The migration rewrites references such as Payments.BillId to match.
  • Fresh installs start empty Claude's call. SeedData.cs holds the developer's real bills and Notion database IDs, and that must never ship in a store build. Seed data moves to a dev-only import or a demo mode.
  • Every synced row records, per field, when it last changed and which device changed it. Times come from a hybrid logical clock (HLC): wall-clock time plus a counter, so the order survives clock skew between devices.
  • Deletes become tombstones, a "deleted at" marker, instead of removing the row. This also solves the existing carryover where Notion archive-on-delete needed a tombstone table.
  • Settings split into two kinds. Synced settings are the pay anchor date, early start, type colours and custom types. Per-device settings are the theme, window size, Notion token and drive sign-in. The canonical list lives in spec/data-model.md.
  • Money stays a double as it is today, unless the conformance suite shows rounding differences between platforms. If it does, switch to integer cents everywhere. The builder decides, with that test as the trigger.

6.2 Merge rule

  • Last write wins per field, ordered by HLC, with ties broken by device ID. If two devices edit different fields of the same bill, both edits survive. If they edit the same field, the later edit wins.
  • Remaining becomes a balance checkpoint plus payments Claude's call. Today "mark paid" lowers Remaining in place and unmark adds it back. Under last-write-wins that loses decrements. Two offline devices paying the same card for different periods would each write "start minus one payment". A statement figure typed in Notion would wipe out payments made in the app. Instead, each bill stores a checkpoint (an amount and the time it was set), and Remaining is the checkpoint minus the payments recorded after it, clamped at zero. Editing Remaining, in the app or in Notion, sets a new checkpoint. What the user sees doesn't change, and Notion's Remaining column is written as the computed value.
Example: one card across three devices
Checkpoint · typed from statement, Oct 3$1,240.00
Mark paid · Oct 16 period · Windows− $85.00
Mark paid · Oct 30 period · iPhone, offline− $85.00
Mark paid · Oct 30 period · Mac, same paymentmerged · $0.00
Remaining on every device$1,070.00
  • Payments merge as a set. Each payment is its own row, so concurrent payments all survive. The regular "mark paid" payment for a bill in a period gets a deterministic ID derived from the bill ID and period key. If two devices mark the same bill paid in the same period, that produces one payment, not two. Extra or one-time payments, a §9 feature candidate, get random IDs and simply add up. Unmark tombstones the deterministic payment.
  • Other payment fields edited on two devices resolve per field, like bills.
  • The merge must be deterministic. The same set of changes, applied in any order, produces the same database on every platform. This is the core of the conformance suite.

6.3 What goes in the drive

<app folder>/PayDay/
├── vault.json                # format version, key generations (id + check value), created-at; no secrets
├── devices/
│   └── <deviceId>/
│       ├── 000001.chg        # encrypted batch of changes, append-only
│       └── 000002.chg
└── snapshots/
    └── <hlc>-<deviceId>.snap # encrypted full state, written periodically for fast first sync
  • Each device writes only its own folder, so two devices never fight over the same file.
  • A device reads everyone else's new files, merges them, and records how far it has read.
  • Compaction: any device may write a snapshot. Files older than the newest snapshot that every known device has read past can be removed. The builder sets the thresholds.
  • Drive locations: the OneDrive app folder (approot), the Google Drive appDataFolder, and the Dropbox App folder. Files count toward the user's own storage, and the data is tiny.

6.4 Encryption and keys

  • One random 256-bit vault key, created on the first device.
  • Files are encrypted with AES-256-GCM with a fresh random nonce per file Claude's call. It's built into .NET, CryptoKit and Android's crypto APIs, so no platform needs a third-party crypto library. The exact framing (header, nonce, ciphertext, tag) is fixed in spec/sync-protocol.md, with test vectors in spec/conformance/.
  • The vault key lives in the OS keystore on each device and is never written to the drive. On Windows that's Credential Manager, the same store the Notion token uses today; on Apple it's the Keychain; on Android it's the Android Keystore.
  • Key generations Claude's call. Every file header names the key generation it was encrypted with, and vault.json lists the generations. v1 ships with one generation and no "remove device" screen. The format still allows rotating to a new key later to cut off a lost or stolen device, which also means signing that device out of the drive provider. Rotation issues a new recovery phrase.
  • Recovery phrase Claude's call. The vault key is shown once as a list of words. If someone loses every device and the phrase, nobody can recover the synced data. That's the price of no one else being able to read it. The onboarding screen says so plainly and offers a local JSON export as a second safety net.

6.5 Setup flows

First device

  1. Turn on sync, pick OneDrive, Google Drive or Dropbox, and sign in on that provider's page.
  2. The app creates the vault, uploads the current data and shows the recovery phrase to save.

Next device

  1. Choose "I already use PayDay" and sign in to the same provider.
  2. Unlock by scanning a QR code shown on an existing device, or by typing the recovery phrase on a PC without a camera.
  3. The data appears.

A device that already has its own data and joins an existing vault Claude's call: v1 doesn't merge two independent databases. The app saves the device's current data as a JSON backup file, then replaces it with the vault's data, and says so before it does. Merging two histories that were never synced would mean matching bills by name and guessing at payments, which isn't worth the risk of silent errors.

Restoring a JSON backup with sync on Claude's call means "make every device look like this backup." The restore is written as new edits: every restored field gets a fresh HLC stamp, and every row missing from the backup gets a tombstone. That way it reaches every device and the next sync doesn't undo it. The app asks for confirmation first and saves the current state as a backup. Per-device settings in the backup apply only to the device doing the restore.

6.6 Provider order

OneDrive first Claude's call. It works on Windows, Mac, iOS and Android, and the existing user is on Windows. Google Drive comes second, since it's common for Android users, and Dropbox third. iCloud (CloudKit) comes only later, as a convenience for Apple-only users, because it can't reach Windows or Android.

6.7 The web app as a device

  • The browser is one more device. It has its own local database and its own folder in the vault, and it follows the same merge and encryption rules. Vercel serves only the app's files and never sees any data.
  • The local database is SQLite compiled to WebAssembly, kept in the browser's private file storage (OPFS). Encryption uses WebCrypto AES-256-GCM, with the same file framing as the other apps byte for byte.
  • Browsers have no OS keystore, so the vault key is kept as a non-extractable WebCrypto key in IndexedDB.
  • Drive sign-in happens in the browser with PKCE, which needs no secret. Microsoft, Google and Dropbox all support it for browser apps.
  • Real use on the web requires sync Claude's call. The browser can erase its storage, so the drive holds the real copy and the browser holds a working copy. If the browser is wiped, the user signs in, unlocks again with the QR code or recovery phrase, and the data comes back. The app also asks the browser for persistent storage and suggests installing it as an app.
  • Try-it mode: without signing in, the web app opens with clearly labelled sample data. Someone can see what it does before installing anything or connecting a drive.
  • The same site hosts the product's landing page, privacy policy and terms, which the app stores and the Notion integration require.

7Notion connector

  • Notion stops being how devices sync and becomes an optional connector. PayDay's data flows out to Notion, and Notion edits to bills flow back in as ordinary changes.
  1. Click Connect Notion.
  2. Notion's consent page opens, and the user picks a page.
  3. PayDay creates the Bills, Payments and Snapshots databases under that page with the right columns. There's no token to paste and no columns to rename.
  • Notion sign-in exchange: a Vercel Function in the web app's project (apps/web) holds the client secret Claude's call. Vercel is already paid for and hosts the web app, so this keeps everything with one vendor instead of adding Cloudflare. The function exchanges the authorization code for tokens, refreshes them, and stores nothing. Native apps receive the result through a custom URL scheme: protocol activation on Windows, a URL scheme on Apple, an intent filter on Android. The scheme's name will follow the product name. The web app receives the result on a normal redirect page.
  • Notion page IDs are stored in the synced data, so any device can run the connector without creating duplicates. The Notion token itself stays per device. The builder decides which device runs the connector and how two connected devices avoid pushing twice. The simplest acceptable answer: the device that connected Notion owns the connector, and the others show "Notion: connected on <device>".
  • The developer's current three databases get adopted rather than recreated, since the connector can be pointed at existing databases.
  • A Notion public integration needs a privacy policy and a terms page. The app stores need those anyway.

8Shared conformance suite

spec/conformance/ holds JSON fixtures, each an input and its expected output. Every app's test project loads the same files. The first fixtures are generated from the current C# behaviour, which is the reference implementation:

  • Pay periods: the anchor date, the 14-day walk, This, Next and Following, and the 3 PM early start.
  • Bill-to-period assignment, totals, and subtotals that exclude inactive bills.
  • Payoff ordering (time-to-payoff, snowball, avalanche) and payoff dates.
  • Merge scenarios: concurrent field edits, delete against edit, duplicate mark-paid, out-of-order delivery.
  • Encryption test vectors and file framing.
  • Backup JSON round-trip, including the legacy cost and owed keys.

Any change to a rule or format lands in spec/ and its fixtures first, then in each app.

9Build order

  1. Restructure the repo to the §5 layout with no behaviour change. First merge wip/backup-2026-09-09 into main (it's one commit ahead and holds only Serena and tooling files), then work on a feature/ branch.
  2. Lock in the product name: FutureCheck Decided. "PayDay" was crowded in the stores, suggested payday loans, and is a video-game franchise. "Check" means both the paycheck and the checkmark on a paid bill, and "Future" points at the forecast. A web search on 2026-11-14 found no app named FutureCheck on the App Store, Google Play or Microsoft Store. Still to do:
    • US trademark: the user searched USPTO tmsearch on 2026-11-14. "FutureCheck" returned no results. "Future Check" returned only marks containing one of the two words, and none for the phrase. That's a clean first pass, not a legal clearance, so a trademark attorney's knockout search is worth doing before spending on marketing.
    • The user registers futurecheck.app, which was available on 2026-11-14, through their existing registrar, Squarespace. Optionally they also register futurecheck.money to protect the name. futurecheck.com is taken. DNS then points the domain at the web app's Vercel project.
    • Use the name everywhere it's needed: the Notion public integration, the custom URL scheme (futurecheck://), the bundle and package IDs (dev.quantumink.futurecheck) Claude's call, and the store listings. Until the domain is live, payday.quantumink.dev serves for testing. The code keeps the PayDay name internally until a rename pass, which the builder schedules. The Windows MSIX package identity (Identity Name in Package.appxmanifest) is NOT changed by the rename pass, because changing it orphans the installed app's LocalState data. The bundle and package IDs dev.quantumink.futurecheck apply to the new Apple and Android apps, and any Windows identity change needs a data migration first.
  3. Scope new features in their own short design (shortlist below) Claude's call. This happens before the sync format is frozen, because features like extra payments, income tracking and set-asides add synced data. Deciding them first avoids migrating a live format across devices.
  4. Write spec/ and the first conformance fixtures from the C# core plus the chosen features' data, and wire them into PayDay.Tests.
  5. Sync in the Windows app: ID migration, balance checkpoints, HLC and tombstones, change files, encryption, OneDrive, and the setup and pairing screens. The exit test is two Windows installs, the VM and the rig, syncing with each other.
  6. Notion connector rework: the sign-in function on Vercel, auto-created databases, and adopting existing ones.
  7. macOS app in SwiftUI with PayDayKit, at feature parity with Windows, passing the conformance suite and syncing with Windows.
  8. Web app in TypeScript, served as static files from Vercel, passing the conformance suite. It includes try-it mode and the landing, privacy and terms pages Claude's call to place it after the Mac app.
  9. iOS app from the same PayDayKit.
  10. Android app in Kotlin with Jetpack Compose and SQLite, passing the conformance suite.
  11. Google Drive, then Dropbox providers.
  12. Phase 8, ship: store listings, signing, and the MSIX, App Store and Play builds.

Feature shortlist

From research done on 2026-11-14, strongest first. The chosen features are built on Windows during or after step 5 and are part of the parity target for the Mac and web apps.

  1. Due-date reminders, with mark paid from the notification or a widget
  2. A forecast of what's left across upcoming paychecks, plus a safe-to-spend number
  3. Set-asides for yearly or irregular bills
  4. Income tracking, including irregular pay and two incomes
  5. Extra or one-time debt payments, and target-date payoff
  6. Payment confirmation numbers, plus CSV and PDF export
  7. Sharing a plan with a partner

10Left to the builder

  • The web framework (Vite or a Next.js static export) and which SQLite-in-browser library to use.
  • Platform minimums (macOS, iOS and Android versions) and the Swift persistence library: GRDB or raw SQLite, not SwiftData, so the schema stays identical to Windows. Android persistence: Room or SQLDelight.
  • The exact HLC encoding, file framing, compaction thresholds and sync triggers (on launch, on change with a debounce, periodically while open).
  • The recovery-phrase word list and length.
  • How each app shows sync status and errors.
  • Whether the Windows Notion code is refactored into the new connector or rewritten.

11Seeding the vault from the developer's installs

The code is built on the rig and ported from there. The arm64 VM is where the app is tested and used, and it probably has the most recent data. That comes from the user on 2026-11-14 and isn't certain.

  1. Before sync is turned on in step 5, export a JSON backup from both the VM and the rig.
  2. A small comparison script reports the newest UpdatedAt per bill, payment counts with the latest PaidAt, and the latest snapshot. The user picks the starting device from that report.
  3. The expected result is that the VM seeds the vault. The rig then joins as the second device, with its data saved to a backup file first (§6.5).
  4. If both sides have edits that matter, they get combined by hand into the seed device's data before sync starts. v1 has no automatic merge of independent histories.

Both backups are kept outside the repo, because they contain real financial data. No open questions remain.
